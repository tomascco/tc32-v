# TC32-V

> [!NOTE]
> **About AI use in this repository.** All of the repository infrastructure (Makefile,
> tool setup scripts, CI and verification environment) was built with AI. The example
> counter (`rtl/tc32v_counter.sv` and `tb/tc32v_counter_tb.sv`) was also written by AI,
> as a template. Everything else, meaning all of the RTL, testbenches and the rest of the
> design work, is and will be written by a human.

An RV32 RISC-V core written from scratch in SystemVerilog. It is a personal project for
learning and for my portfolio, during my graduate studies in Digital Microelectronics at UFSM.

## Roadmap

- **Stage 0 (current):** small modules (ALU, register file, counter, UART TX) and the
  verification environment.
- **Milestone 1:** single-cycle RV32I (chapter 7 of Harris & Harris) running `riscv-tests`
  and a C program.
- **Milestone 2:** 5-stage pipeline; co-simulation against Spike.
- **Milestone 3:** M and A extensions, Zicsr, Wishbone, riscv-arch-test and riscv-formal.
- **Milestone 4:** S/U modes, Sv32 MMU and Linux.
- **Later:** a separate chip repository, generated from the wafer.space GF180MCU template
  (LibreLane), instantiates this core as a submodule.

## Host prerequisites

- `g++` 10 or newer (or `clang++` 5 or newer). Verilator uses C++20 coroutines for
  `--timing`.
- `make`.
- `perl`, because the `verilator` executable is a Perl script.
- Optional: `ccache`. If it is on the PATH, the Makefile uses it automatically (see below).

No root access is needed. If the system compiler is too old,
`make tools` lists the alternatives: a `gcc-toolset` already installed by the
administrator, or `gxx` from conda-forge through micromamba. To pick another compiler:

```sh
CXX=/opt/rh/gcc-toolset-12/root/usr/bin/g++ make tools
CXX=/opt/rh/gcc-toolset-12/root/usr/bin/g++ make test
```

## Installation

```sh
make setup
```

That is the only step. It runs `make tools`, then `make lint` and `make test` once to prove
the whole flow works on this machine, and prints the next steps.

`make tools` is the part that installs. It downloads the [OSS CAD Suite](https://github.com/YosysHQ/oss-cad-suite-build)
release pinned in `tools.lock`, checks its SHA-256 and extracts it into `.tools/` (inside
the repository, ignored by git). After that, `make test` works from any shell, fish
included, without activating any environment: the Makefile adds
`.tools/oss-cad-suite-<date>/bin` to the `PATH` by itself. The suite also ships GTKWave
and Surfer, so no separate install is needed to view waveforms.

- Running `make tools` again downloads nothing.
- The installation is atomic. If it is interrupted (Ctrl+C), nothing is left half-done;
  just run it again.
- **No access to GitHub** (for example, behind the lab proxy): download the `.tgz` on
  another machine and run `TGZ=/path/oss-cad-suite-linux-x64-YYYYMMDD.tgz make tools`.
  The SHA-256 is checked the same way.
- To keep the tools outside the repository (for example, to share one installation
  between several clones), pass `TOOLS_ROOT=/some/other/place` to every command.
- To remove everything, delete `.tools/`. A `git clean -fdx` also deletes it, and the next
  `make tools` downloads about 700 MB again.

Currently pinned: **2026-10-20**, with Verilator 5.053 (devel, after 5.052),
Yosys 0.70+176 and z3 4.15.5. The **sv-elab** frontend (`read_slang`) is **built into**
Yosys, so the Makefile does not need `-m slang`. The Makefile detects both cases
(built-in or plugin) and fails with a clear message if `read_slang` is missing.
It never falls back to `read_verilog -sv`.

### Updating the stack

1. Pick a date at <https://github.com/YosysHQ/oss-cad-suite-build/releases>.
2. Download its linux-x64 `.tgz` and run `sha256sum` on it.
3. Change `OSS_CAD_SUITE_DATE` and `OSS_CAD_SUITE_SHA256` in `tools.lock`.
4. Run `make tools`.

The old version stays in `.tools/`, because another branch may be pinned to it. To
delete it, run `make tools-prune`.

### ccache

If `ccache` is installed, the Makefile uses it to compile the C++ generated by Verilator.
The cache lives in `.tools/ccache` and is limited to 1 GB. Without `ccache`, nothing changes.

## Commands

| Command | What it does |
|---|---|
| `make setup` | full setup to start coding: `make tools`, `make lint` and `make test` |
| `make tools` | installs the tools from `tools.lock` into `.tools/` |
| `make tools-prune` | deletes OSS CAD Suite versions other than the one in `tools.lock` (asks for confirmation; accepts `KEEP="date1 date2"` and `YES=1`) |
| `make lint` | lints all RTL: Verilator `-Wall` and elaboration with sv-elab |
| `make test` | runs every testbench plus `selfcheck`; stops at the first failure |
| `make test-<module>` | runs one testbench, for example `make test-tc32v_counter` |
| `make selfcheck` | confirms that a failing `assert` gives a non-zero exit code |
| `make synth` | check synthesis with Yosys (`synth_ecp5`); report in `build/synth/` |
| `make waves-<module>` | runs the testbench and writes `build/<module>.fst` (GTKWave or Surfer) |
| `make clean` | deletes `build/` |
| `SEED=N make test` | changes the seed of the random tests (default 1) |

The targets find the modules in `rtl/` and the testbenches in `tb/` by themselves. Files
that do not declare a `module` or `package` yet, such as the `// TODO` placeholders, are
ignored. Once one of them gets a signature, it enters lint, synthesis and tests without
any change to the Makefile.

## Testbenches

`tb/tc32v_counter_tb.sv` is the template for the others. It has directed tests, a random
test with a `rand` class and a reference model, and a covergroup.

Verilator 5.053 limitations found so far:

- **Per-coverpoint `get_coverage()` is not supported** ("Unsupported: Member call on
  object"). Only `get_coverage()` on the whole covergroup works. The per-coverpoint report
  is disabled behind `` `define TC32V_COVERPOINT_REPORT `` in the testbench.
- Even without `-Wall`, some Verilator warnings are errors. For example, using the return
  value of `randomize()` (an `int`) directly as a condition gives `WIDTHTRUNC`: write
  `assert (obj.randomize() == 1)`.
